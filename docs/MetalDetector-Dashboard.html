วิเคราะห์ปัญหาเครื่อง Metal Detector

แบบร่าง dashboard สำหรับหัวหน้างาน / QC / ซ่อมบำรุง — ดูว่าเครื่องไหนมีปัญหา ปัญหาเกิดจากอะไร เกิดตอนไหน และกระทบการผลิตเท่าไร ข้อมูลจำลอง

ประเด็นที่ต้องดูก่อน

สรุปอัตโนมัติจากกราฟด้านล่าง ตามตัวกรองที่เลือก

    1แนวโน้มการคัดออก (Reject)

    ปัญหาเพิ่มหรือลดลง? คัดออกหลอก (ตรวจซ้ำไม่พบโลหะ) มากกว่าพบโลหะจริงแค่ไหน?

    ข้อมูล: ✓ มีใน PFCM รายการที่ผ่าน MD (md, md_no, md_time) + ต้องเก็บเพิ่ม บันทึก Reject + ผลตรวจซ้ำ

    2Pareto สาเหตุปัญหา

    แก้สาเหตุไหนก่อนแล้วปัญหาหายมากที่สุด?

    ข้อมูล: + ต้องเก็บเพิ่ม สาเหตุจากรายการมาตรฐาน (dropdown)

    3ผลตรวจ Test piece รายชั่วโมง (Fe 1.5 · Non-Fe 2.0 · SUS 2.5 mm)

    ทุกเครื่องตรวจครบทุกรอบไหม? รอบไหนไม่ผ่าน และต้องกักสินค้าย้อนไปถึงรอบไหน?

    ข้อมูล: + ต้องเก็บเพิ่ม ผล Test piece ทุกรอบ (หรือดึงจากใบตรวจ F3QCPF06 ใน DocHUB ถ้ามีช่องนี้)

    4สาเหตุ × เครื่อง

    แต่ละเครื่องมีปัญหาเรื่องอะไร? (เครื่องเฉพาะ vs ปัญหาร่วมทุกเครื่อง)

    ข้อมูล: ✓ มีใน PFCM Master MetalDetectors / WorkAreas + ต้องเก็บเพิ่ม สาเหตุ

    5ช่วงเวลาที่เกิดปัญหา (วัน × ชั่วโมง)

    ปัญหากระจุกตอนไหน? หลังล้างเครื่อง, ตอนเปลี่ยนรุ่นสินค้า หรือกะดึก?

    ข้อมูล: + ต้องเก็บเพิ่ม เวลาเกิดเหตุจากบันทึกเหตุการณ์

    6Downtime ต่อเครื่อง

    เครื่องไหนหยุดนานสุด? เสียบ่อย (MTBF ต่ำ) หรือซ่อมนาน (MTTR สูง)?

    ข้อมูล: + ต้องเก็บเพิ่ม เวลาเริ่ม–จบที่เครื่องหยุด (หรือจากระบบแจ้งซ่อม)

    7อัตราคัดออกหลอกตามสินค้า

    สินค้าไหนทำให้เครื่องคัดออกหลอกบ่อย (Product effect) จนต้องปรับค่าโปรแกรมสินค้า?

    ข้อมูล: ✓ มีใน PFCM สินค้าของรายการ (mapping_id → Production.code) + ต้องเก็บเพิ่ม Reject

    8เวลารอผ่าน MD

    รถเข็นรอผ่าน MD นานแค่ไหน? กี่ % เกินมาตรฐานจนเป็น Delay?

    ข้อมูล: ✓ มีใน PFCM qc_datetime ตอน QC บันทึก "รอผ่าน MD" → md_time ตอนผ่าน MD

    9ค่าสัญญาณ Test piece Fe — MD-03

    ความไวของเครื่องลดลงเรื่อย ๆ ก่อนจะตรวจไม่เจอไหม? (เตือนล่วงหน้าเพื่อนัด Calibrate)

    ข้อมูล: ⚙ ต่อข้อมูลจากเครื่อง ค่าสัญญาณที่เครื่องส่งออก (Phase 3)

    บันทึกเหตุการณ์ล่าสุด

    เหตุการณ์ที่เกิดขึ้นจริงพร้อมการแก้ไข — ใช้ตามงานต่อและเป็นหลักฐาน audit

    ข้อมูลที่ต้องใช้ในแต่ละกราฟ

    PFCM บันทึกแค่ว่ารายการ "ผ่าน MD" หรือ "รอผ่าน MD" (ตาราง QC: md, mdcheck, md_no, WorkAreaCode, md_time, md_remark) ยังไม่มีบันทึกว่าเครื่องมีปัญหาอะไร กราฟส่วนใหญ่จึงต้องมีฟอร์มบันทึกเหตุการณ์ MD เพิ่มอีก 1 ฟอร์ม

    #กราฟรูปแบบข้อมูลที่ต้องใช้สถานะข้อมูล
    —ตัวเลขสรุป (KPI)Stat tile + เทียบช่วงก่อนหน้าจำนวนรายการที่ผ่าน MD, Reject, Test piece, downtime, เวลารอบางส่วนมีแล้ว / ที่เหลือต้องมีฟอร์มบันทึก
    1แนวโน้มการคัดออกแท่งซ้อน รายวัน/สัปดาห์Reject แต่ละครั้ง + ผลตรวจซ้ำ (พบ / ไม่พบโลหะ), จำนวนรายการที่ผ่าน MD+ ต้องเก็บเพิ่ม
    2Pareto สาเหตุแท่งแนวนอนเรียงมาก→น้อย + % สะสมสาเหตุ (เลือกจากรายการมาตรฐาน)+ ต้องเก็บเพิ่ม
    3ผล Test piece รายชั่วโมงตารางสถานะ เครื่อง × ชั่วโมงผล Fe / Non-Fe / SUS ทุกรอบ, ผู้ตรวจ, เวลา+ ต้องเก็บเพิ่ม หรือดึงจาก F3QCPF06 (DocHUB)
    4สาเหตุ × เครื่องHeatmapmd_no + สาเหตุ+ ต้องเก็บเพิ่ม
    5ช่วงเวลาที่เกิดปัญหาHeatmap วัน × ชั่วโมงเวลาเกิดเหตุ+ ต้องเก็บเพิ่ม
    6Downtime ต่อเครื่องแท่งแนวนอน + MTBF/MTTRเวลาเริ่ม–จบที่เครื่องหยุด, สาเหตุ+ ต้องเก็บเพิ่ม หรือระบบแจ้งซ่อม
    7คัดออกหลอกตามสินค้าแท่งแนวนอน + เส้นเป้าสินค้าของรายการ (mapping_id → Production.code) + Reject✓ มีใน PFCM + Reject
    8เวลารอผ่าน MDHistogram + เส้นมาตรฐานqc_datetime (บันทึก "รอผ่าน MD") → md_time✓ มีใน PFCM
    9ค่าสัญญาณ Test pieceเส้น + ระดับตัดสิน/เตือนค่าสัญญาณที่เครื่องส่งออก (export / Modbus / OPC-UA แล้วแต่รุ่น)⚙ ต่อข้อมูลจากเครื่อง

    ฟอร์มบันทึกเหตุการณ์ MD (ข้อมูลที่ต้องเก็บเพิ่ม)

    • วันเวลา, เครื่อง, พื้นที่ — เลือกจาก master MetalDetectors / WorkAreas ที่มีอยู่แล้ว (หน้า MDmanage)
    • ประเภท — คัดออก (Reject) · Test piece ไม่ผ่าน · เครื่องหยุด · ไม่ได้ตรวจตามรอบ
    • ผลตรวจซ้ำหลังคัดออก — พบโลหะ (Fe / Non-Fe / SUS, ขนาด mm) หรือไม่พบ (= คัดออกหลอก)
    • สาเหตุ — เลือกจากรายการมาตรฐาน 9 ข้อ (พิมพ์เพิ่มได้ใน "หมายเหตุ") เพื่อให้นับเป็น Pareto ได้ ถ้าพิมพ์อิสระอย่างเดียวจะนับไม่ได้
    • สินค้า — สแกน QR สลีป → code / batch ผ่าน /api/export/mapping/:mapping_id ที่มีอยู่แล้ว
    • เวลาเริ่ม–จบที่เครื่องหยุด, การแก้ไข, ผู้บันทึก — ผู้บันทึกได้จาก token ของผู้ใช้ (req.user)
    • ผล Test piece รายชั่วโมง — Fe / Non-Fe / SUS ผ่านหรือไม่ผ่าน, ผู้ตรวจ

    ทำทีละขั้น

    Phase 1 · ใช้ข้อมูลที่มีอยู่KPI จำนวนรายการผ่าน MD, เวลารอผ่าน MD (กราฟ 8), จำนวนรายการต่อสินค้า/เครื่อง — ทำได้เลยจากตาราง QC
    Phase 2 · เพิ่มฟอร์มบันทึกเหตุการณ์กราฟ 1–7 + บันทึกเหตุการณ์ — ฟอร์มสั้น ๆ ข้างเครื่อง MD (แท็บเล็ต / สแกน QR สลีป)
    Phase 3 · ต่อข้อมูลจากเครื่องกราฟ 9 ค่าสัญญาณ / ความไว — ต้องตรวจก่อนว่ารุ่นเครื่องส่งข้อมูลออกได้ทางไหน
