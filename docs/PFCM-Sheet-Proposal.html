  • แนวคิดหลัก: ทุกอย่างในระบบคือ "ชีต" (ตาราง) หน้าตาเหมือน Excel — ตาราง Flow ของ RM, ข้อมูลวัตถุดิบ, แผนการผลิต, รถเข็น, ช่องจอด ฯลฯ ใช้เครื่องมือเดียวกัน กฎการกรอก สิทธิ์ และประวัติการแก้ไขเหมือนกันทั้งหมด

  • สิ่งที่ต้องสร้างเพิ่ม 6 อย่าง: (1) กติกาการลงข้อมูลต่อคอลัมน์ (2) Tool/Command Registry (3) Delay Engine (4) สิทธิ์ระดับคอลัมน์/ขอบเขตแถว (5) Device Gateway สำหรับ RFID/สแกนเนอร์/เครื่องพิมพ์ (6) ตัวนำเข้า/สะพานข้อมูลจาก PFCM เดิม
  • วิธีเปลี่ยนระบบที่แนะนำ: ค่อยๆ ย้ายทีละงาน (strangler) ไม่ปิดระบบเดิมในวันเดียว เพราะระบบเดิมใช้งานจริงบนสายการผลิตและมี RFID ที่ต้องเชื่อมต่อต่อเนื่อง

3โครงสร้างพื้นที่งาน: "ทุกอย่างคือชีต"

จับคู่หน้าเดิมของ PFCM (ซึ่งแยกตามบทบาท 7 โมดูล มีไฟล์ซ้ำจำนวนมาก) เป็นชีตไม่กี่ชุด

📁 PFCM
├─ 📁 งานประจำวัน (Operations)
│   ├─ 📊 RM Flow Board            ← ชีตหลัก 1 แถว = วัตถุดิบ 1 ตัว (mapping_id) เห็นทุกขั้นในบรรทัดเดียว
│   ├─ 📊 รอบห้องเย็น (Cold Rounds) ← ชีตลูก 1 แถว = 1 รอบเข้า-ออก (แทน come_cold_date / _two / _three)
│   └─ 📊 กล่องรอผูก EPC (RFID Inbox)
├─ 📁 ข้อมูลหลัก (Master Data)     ← หน้า Sup เดิมมาอยู่รูปแบบเดียวกัน
│   ├─ 📊 วัตถุดิบ (RawMat)  + เวลามาตรฐาน (PTC / Cold / Rework)
│   ├─ 📊 แผนการผลิต (Production Plan)
│   ├─ 📊 รถเข็น (Trolley) / ผูก EPC ↔ tro_id
│   ├─ 📊 ห้องเย็นและช่อง (ColdStorage / Slot)
│   └─ 📊 ผู้ใช้ / จุดงาน (Users / Workplace)
├─ 📁 รายงาน (Reports)            ← มุมมอง/Dashboard ที่บันทึกไว้ (Delay, ประวัติ, การใช้บรรจุภัณฑ์)
└─ 📁 ตั้งค่าระบบ (Tools, Rules, Devices)
ข้อดี: เพิ่มข้อมูลหรือคอลัมน์ใหม่ (เช่น "อุณหภูมิตอนรับเข้า") ทำจากหน้าเว็บ ไม่ต้องแก้โค้ดและ deploy และทุกชีตมีสิทธิ์ ประวัติ และ rollback แบบเดียวกัน

4หน้าตา RM Flow Board (ภาพจำลอง)

คอลัมน์จัดกลุ่มตามขั้นตอน หัวคอลัมน์บอกวิธีลงข้อมูล เซลล์บอกสถานะด้วยสี — เห็น flow และ Delay ในหน้าเดียว

พฤติกรรมของเซลล์

  • กดเซลล์ที่ถึงคิว → ช่องกรอกพอดีกับกติกาของคอลัมน์ (ช่องสแกน, dropdown, ตัวเลข, หรือปุ่ม Tool) ไม่ใช่ช่องข้อความอิสระ
  • ขั้นต่อไปปลดล็อกเมื่อขั้นก่อนหน้าเสร็จ (กำหนดเป็นเงื่อนไขของคอลัมน์ได้)
  • เซลล์ที่คนอื่นหรือ RFID เพิ่งแก้ จะกะพริบ (DocHUB มี remote edit flash อยู่แล้ว) และถ้าชนกันให้ขึ้น "ข้อมูลเปลี่ยนแล้ว" แทนการเขียนทับ
  • บนมือถือ/เครื่องสแกน: แสดงเป็นมุมมองการ์ดของแถวเดียวที่เน้นเฉพาะเซลล์ที่ต้องกรอก (ตารางเต็มเหมาะกับหัวหน้างาน/ผู้ดูแล)

5กติกาการลงข้อมูลต่อคอลัมน์ (Entry Rules)

เพิ่มช่อง entry ในนิยามคอลัมน์ (JSON) ตั้งได้จากหน้าเว็บ โดย server เป็นผู้บังคับใช้ทุกครั้ง

โหมดความหมายตัวอย่างใช้กับ
type ⌨️พิมพ์/เลือกเองได้ ตรวจรูปแบบตาม validationผู้เตรียม, หมายเหตุ
scan 📷ต้องสแกนเท่านั้น (ปิดการพิมพ์) ระบุชนิดที่ยอมรับ + วิธีแปลงค่ารับบรรจุ = สแกน QR ป้ายทะเบียน หรือ QR สลีป
scan_or_typeสแกนหรือพิมพ์ก็ได้ (เหมือนหน้า Check In Pack ที่เพิ่งทำ: QR ป้ายทะเบียน / QR สลีป / พิมพ์ mapping_id)ยืนยันรถเข็น
tool 🔧ห้ามแก้เซลล์ตรงๆ ต้องกดปุ่ม Tool ที่ผูกไว้ ซึ่งทำงานหลายอย่างในธุรกรรมเดียวเข้าห้องเย็น (จองช่อง+บันทึกเวลา), ส่งออก (เคลียร์ช่อง+พิมพ์สลีป)
device 🤖เฉพาะอุปกรณ์ที่ลงทะเบียนเขียนได้ (RFID reader ฯลฯ) ผู้ใช้แก้มือไม่ได้ ยกเว้นบทบาทที่อนุญาต "แก้ไขกรณีพิเศษ" (มี audit)เวลาเข้า/ออกห้องเย็นอัตโนมัติ
computed ƒคำนวณจากคอลัมน์อื่น ห้ามกรอกDelay, ระยะเวลาอยู่ห้องเย็น
{
  "column_name": "รับบรรจุ",
  "data_type": "varchar",
  "entry": {
    "mode": "scan_or_type",
    "accept": [
      { "kind": "tro_id",        "pattern": "^\\d{4}$",                      "resolve": "trolley.by_id" },
      { "kind": "slip_qr",       "pattern": "^.+\\|.+\\|.+\\|(\\d+)\\|",   "resolve": "mapping.by_id" },
      { "kind": "mapping_id",    "pattern": "^\\d{4,10}$",                   "resolve": "mapping.by_id" }
    ],
    "must_match_row": "tro_id",             // ค่าที่สแกนต้องเป็นของแถวนี้
    "requires": ["เข้าห้องเย็น", "ออกห้องเย็น"], // คอลัมน์ที่ต้องมีค่าก่อน
    "allow_manual_override": { "roles": ["supervisor"], "reason_required": true }
  },
  "permissions": { "view": ["*"], "edit": ["pack_operator", "supervisor"] }
}
หลักการ: หน้าเว็บแสดงช่องกรอกตาม entry เพื่อความสะดวก แต่ server ตรวจซ้ำทุกคำขอ — ถ้าส่ง API ตรงๆ ก็ผ่านกติกาเดียวกัน ผลคือกติกา "ต้องสแกน" บังคับได้จริง ไม่ใช่แค่ซ่อนปุ่ม

Tool Registry (คำสั่งที่ทำหลายอย่างในครั้งเดียว)

ตรรกะธุรกิจเดิมของ PFCM (เข้า/ออกห้องเย็น, จองช่อง, พิมพ์สลีป, รับเข้าบรรจุ) ย้ายมาเป็น "Tool" ที่ลงทะเบียนชื่อไว้ คอลัมน์ผูกกับ Tool ได้จากหน้าเว็บ ส่วนตรรกะข้างในเป็นโค้ดที่ทดสอบแล้ว ไม่ให้ผู้ใช้เขียนเอง

tool: "cold.checkin"
  input:  { mapping_ids[], reader_no? }
  checks: สถานะต้องเป็น (stay_place = จุดเตรียม, dest = รอCheckin) ฯลฯ
  does:   อัปเดตสถานะ → จองช่องใน cs_id ที่กำหนด → บันทึกรอบ → แจ้งเรียลไทม์   (ทั้งหมดในธุรกรรมเดียว)
  idempotency_key: reader_no + epc + window   // กันสแกนซ้ำ

6ระบบ Delay (กำหนดจากคอลัมน์ได้เอง)

Delay คือ "กติกาเวลา" ที่ผูกกับคอลัมน์ ตั้งจากหน้าเว็บ ไม่ฮาร์ดโค้ดเหมือนระบบเดิม

{
  "delay_rule": {
    "name": "อยู่ห้องเย็นเกินมาตรฐาน",
    "start":   { "column": "เข้าห้องเย็น" },
    "stop":    { "column": "ออกห้องเย็น", "or": "now" },       // ยังไม่ออก = นับถึงปัจจุบัน
    "limit":   { "from": "lookup", "sheet": "วัตถุดิบ", "key": "mat", "column": "cold_std_hr" },
    "warn_at": 0.8,                                              // เตือนที่ 80% ของเวลาที่กำหนด
    "pause_when": [ { "column": "สถานะ", "in": ["รอ QC"] } ],  // หยุดนับ (เช่นรอตรวจ)
    "calendar": "24h",                                           // หรือปฏิทินกะ/วันหยุด
    "notify": { "over": ["supervisor"], "channel": ["in_app", "line"] }
  }
}
  • ผลลัพธ์เป็นคอลัมน์ ƒ (เช่น "เหลือเวลา", "เกิน") ใช้กรอง/เรียง/ทำกราฟได้เหมือนคอลัมน์ปกติ จึงเรียงแถวตาม Delay ได้ทันที
  • เวลามาตรฐานมาจากชีตข้อมูลหลัก (ตารางวัตถุดิบ) เปลี่ยนมาตรฐานที่ที่เดียว ทุกแถวที่เกี่ยวข้องเปลี่ยนตาม
  • รองรับกติกาเดิม: PTC (เตรียม→ห้องเย็น), Cold (อยู่ห้องเย็น), Rework, Mix time, หลายรอบ (รอบ 1–3) — แต่ละอย่างเป็น 1 rule
  • วิธีคำนวณ: บันทึกค่า "เวลาครบกำหนด" (due_at) ลง DB ตอนเซลล์เปลี่ยน แล้วให้ worker ตรวจเป็นระยะและส่ง event (ไม่คำนวณใหม่ทุกครั้งที่เปิดหน้า) เพื่อให้เร็วและแจ้งเตือนได้แม้ไม่มีใครเปิดเว็บ

7Flow ของ RM และความสัมพันธ์ระหว่างชีต

แผนผลิต→เตรียม→ ห้องเย็น (หลายรอบ)→อบ / ผสม→ QC→บรรจุ
  • 1 แถว = 1 mapping_id (คงรหัสเดิม) เพื่อให้เทียบกับระบบเดิมและสลีปที่พิมพ์ไปแล้วได้ (QR สลีปมี mapping_id)
  • รอบห้องเย็นแยกเป็นชีตลูก แทนคอลัมน์ซ้ำ ×3 — รองรับกี่รอบก็ได้ และรายงานง่ายขึ้น (ชีตหลักแสดงรอบล่าสุดผ่านคอลัมน์ lookup)
  • วัตถุดิบผสม = แถวแม่ (mix_code) + แถวลูกอ้างอิง mapping_id ของส่วนผสม (คอลัมน์ชนิด relation)
  • คอลัมน์ชนิดใหม่: relation (อ้างชีตอื่น), lookup (ดึงค่าจากชีตอื่น), scan, duration, status (มีลำดับ/สี/ขั้นตอนถัดไป)
  • มุมมองตามบทบาท (Saved Views): ทุกบทบาทเปิดชีตเดียวกัน แต่มีมุมมองที่กรอง/ซ่อนคอลัมน์ไว้ให้ ("ห้องเย็น: รอเข้า", "บรรจุ: รอรับ", "ผู้ดูแล: ที่เกิน Delay") แทนการสร้าง 7 โมดูลแยก

8การรองรับ RFID

RFID Reader (TCP)→Device Gateway (fork เดียวต่อ reader)→ Ingest API (idempotent)→Tool: cold.checkin / cold.checkout→เซลล์กะพริบ + พิมพ์สลีป
  • Device Gateway แยกเป็น service เดียวต่อ reader (ข้อจำกัดฮาร์ดแวร์เดิม: ห้ามต่อซ้อนหลาย process) ทำหน้าที่แยกเฟรม กรอง EPC ขยะ ตรวจ watchdog — พอร์ตมาจาก RFIDc1.js และ rfidFrameParser.js ที่ทดสอบแล้ว
  • เขียนข้อมูลผ่านทางเดียวกับผู้ใช้ ในนามผู้ใช้ระบบ device:reader-1 ใช้ Tool และกติกาชุดเดียวกัน จึงมี audit/rollback ครบ (หมายเหตุ: rollback แก้ข้อมูลได้ แต่ย้อนการพิมพ์สลีปหรือการเคลื่อนที่จริงไม่ได้)
  • ชีตข้อมูลหลัก "EPC ↔ รถเข็น" + กล่องรอผูก (EPC ที่ไม่รู้จัก) ใช้การผูก/แก้/ยกเลิกที่ทำไว้แล้ว ย้ายมาเป็นชีตปกติ
  • ตั้งค่า reader จากหน้าเว็บ: IP/พอร์ต, ห้องเย็นที่ให้เลือกช่อง (เช่น cs_id 1–7), เวลา cooldown, เครื่องพิมพ์ปลายทาง — เก็บเป็นชีตตั้งค่า
  • พิมพ์สลีป: เป็น Tool ฝั่ง server เรียก print-agent เอง ไม่ต้องมีเบราว์เซอร์เปิดค้างไว้ (ข้อมูลสลีปถูก snapshot ก่อนรถออกจากช่อง) แก้ข้อจำกัดของระบบเดิมที่การพิมพ์ทำฝั่งเบราว์เซอร์

สิทธิ์ 3 ชั้น

  1. ไฟล์/โฟลเดอร์ (มีใน DocHUB แล้ว): ใครเปิดชีตไหนได้
  2. คอลัมน์: ใครเห็น/แก้คอลัมน์ไหน (เช่น "บรรจุ" แก้ได้เฉพาะขั้นบรรจุ)
  3. แถว (scope): เห็น/แก้เฉพาะไลน์หรือจุดงานของตัวเอง (ใช้ wp_id เดิม)
จุดที่ต้องตัดสินใจเรื่องประสิทธิภาพ: DocHUB เก็บค่าเซลล์แบบ EAV (1 แถวใน Cells ต่อ 1 เซลล์) ยืดหยุ่นมาก แต่ที่ปริมาณหลายแสนแถว × หลายสิบคอลัมน์ พร้อม RFID เขียนต่อเนื่อง การกรอง/รายงานจะหนักกว่าตารางจริง แนวทาง: ทำ proof-of-concept วัดก่อน และถ้าไม่ผ่าน ให้ชีต Flow Board ใช้ "ตารางจริง" (typed table) ที่สร้างจากนิยามคอลัมน์ หรือมี materialized view สำหรับคอลัมน์ที่ค้นบ่อย — ต้องวัดจริง ไม่ควรเดา

11การย้ายจากระบบเดิม

ระบบเดิมคือ production จริง การเปลี่ยนวันเดียวเสี่ยงสายการผลิตหยุด แนะนำย้ายทีละงาน:

  1. สะพานข้อมูลอ่านอย่างเดียว: ชีต Flow Board ดึงข้อมูลจาก TrolleyRMMapping / History เดิมมาแสดงก่อน ใช้พิสูจน์ UX โดยไม่แตะข้อมูลจริง
  2. ย้ายข้อมูลหลัก: วัตถุดิบ, รถเข็น, ช่อง, ผู้ใช้ — นำเข้าแล้วตรวจเทียบจำนวน/ค่า
  3. ย้ายทีละงานที่เขียนข้อมูล (เช่น Check In บรรจุ → ห้องเย็น → ส่งออก) ผ่าน Tool ที่ผลลัพธ์ตรงกับ API เดิม มีช่วงรันคู่ขนานและเทียบผล
  4. ย้าย RFID เป็นขั้นสุดท้าย: หยุด service เดิม 1 ตัว/reader แล้วเปิด Gateway ใหม่ ห้ามรันพร้อมกันสองระบบ (ข้อจำกัดฮาร์ดแวร์)
  5. คงรหัส mapping_id, tro_id, epc เดิม เพื่อให้สลีป ป้าย และประวัติเดิมยังใช้ได้

12แผนงานเป็นระยะ (ไม่ระบุเวลา — ขึ้นกับขนาดทีม)

ระยะ 0
ตรวจสอบฐาน + สัมภาษณ์หน้างาน — ติดตั้ง DocHUB, วัดประสิทธิภาพกับข้อมูลจำลองขนาดจริง, ดูว่าตารางเรนเดอร์แบบ virtualized ไหม, เลือก 3 งานหลักที่จะลองก่อน
ผ่านเมื่อ: ตาราง 100k แถวเลื่อน/กรองลื่น และเลือก EAV หรือ typed table ได้
ระยะ 1
Entry Engine + สิทธิ์ระดับคอลัมน์/แถว — entry_config, ColumnPermissions, RowScopes, ชนิดคอลัมน์ใหม่ (scan, relation, lookup)
ผ่านเมื่อ: ส่ง API ตรงๆ แล้วถูกปฏิเสธตามกติกา
ระยะ 2
Flow Board อ่านอย่างเดียว + สะพานข้อมูลเดิม — Saved Views ตามบทบาท, ให้ผู้ใช้จริงลอง
ผ่านเมื่อ: ผู้ดูแลตอบ "RM นี้อยู่ขั้นไหน/อะไร Delay" ได้จากหน้าเดียว
ระยะ 3
Tool Registry + สแกน + พิมพ์สลีป — พอร์ต Check In บรรจุ / เข้า-ออกห้องเย็น เป็น Tool, รันคู่ขนานเทียบผล
ผ่านเมื่อ: ผลลัพธ์ตรง API เดิม 100% ในชุดทดสอบ
ระยะ 4
Delay Engine — delay_rule, DelayStates, worker, แจ้งเตือน, ย้ายกติกา PTC/Cold/Rework/Mix
ผ่านเมื่อ: ค่า Delay ตรงรายงานเดิมในตัวอย่างข้อมูลจริง
ระยะ 5
Device Gateway + RFID — พอร์ตจาก RFIDc1.js, ชีตตั้งค่า reader, inbox EPC
ผ่านเมื่อ: รันข้างระบบเดิมเงียบๆ (log-only) แล้วผลตรงกัน จึงสลับ
ระยะ 6
Master Data ฝั่ง Sup + Dashboard + ปลดระวางหน้าเดิม — แผนการผลิต, วัตถุดิบ, รายงาน
ผ่านเมื่อ: หน้าเดิมไม่มีผู้ใช้ตามสถิติ จึงปิดทีละโมดูล

13ความเสี่ยงและข้อควรระวัง

ความเสี่ยงผลกระทบแนวทาง
ความอิสระของ "เพิ่มคอลัมน์ได้เองทั้งหมด" ทำให้ข้อมูลหลุดมาตรฐานรายงาน/Delay พัง เมื่อมีคนลบหรือเปลี่ยนชนิดคอลัมน์ที่ถูกอ้างอิงคอลัมน์ "ระบบ" (ล็อกชื่อ/ชนิด) แยกจากคอลัมน์ผู้ใช้; ตรวจ dependency ก่อนลบ/เปลี่ยนชนิด
ประสิทธิภาพ EAV + RFID เขียนต่อเนื่องตารางช้า, deadlockระยะ 0 วัดจริง; ทางเลือก typed table; ธุรกรรมสั้น, ดัชนีที่เหมาะสม
ผู้ใช้หน้างานไม่ถนัดตารางใช้งานช้ากว่าเดิมมุมมองการ์ดสำหรับมือถือ/สแกนเนอร์ + ทดลองกับกลุ่มเล็กก่อน
Rollback ย้อนเหตุการณ์จริงไม่ได้ย้อนข้อมูลแต่สลีปพิมพ์ไปแล้ว/รถเคลื่อนไปแล้วTool บันทึกผลข้างเคียง; rollback แสดงคำเตือน; ใช้ "แก้ไขพร้อมเหตุผล" แทนการย้อนในงานที่มีผลทางกายภาพ
รันสองระบบพร้อมกันตอนเปลี่ยนผ่านข้อมูลไม่ตรงกัน, RFID ชนกันกำหนดแหล่งความจริงต่องาน (source of truth) ทีละงาน; RFID สลับครั้งเดียว
ความพร้อมใช้งานจริงของ DocHUBอาจยังไม่ผ่านการใช้งานจริงที่ปริมาณสูง/ความปลอดภัยทบทวนโค้ด/ทดสอบโหลด/security review ก่อนยึดเป็นฐาน

14คำถามที่ต้องตัดสินใจก่อนเริ่ม

  1. ฐานระบบ: สร้างบน DocHUB (fork) หรือเขียนใหม่ทั้งหมดโดยยืมแนวคิด? (แนะนำ fork เพราะประหยัดเวลามากและแก้ปัญหา auth/สิทธิ์/ประวัติไว้แล้ว)
  2. 1 แถวคืออะไร: 1 mapping_id (แนะนำ) หรือ 1 รถเข็น?
  3. ผู้ใช้หลักของตารางเต็ม: ผู้ดูแล/หัวหน้างาน หรือพนักงานหน้างานด้วย (ถ้าด้วย ต้องทำมุมมองการ์ดมือถือตั้งแต่ระยะแรก)
  4. ตารางสิทธิ์: บทบาทไหนแก้คอลัมน์/ขั้นไหนได้, แก้ย้อนหลังได้ไหม, ใครอนุมัติ?
  5. กติกาเวลา Delay: นับเวลา 24 ชม. หรือตามกะ/วันหยุด? มีสถานะ "หยุดนับ" อะไรบ้าง? แจ้งเตือนช่องทางไหน (ในระบบ/LINE/อีเมล)?
  6. ข้อมูลเดิม: ย้ายประวัติย้อนหลังกี่ปี หรือเก็บระบบเดิมไว้อ่านอย่างเดียว?
  7. ผู้ดูแลระบบ: ใครเป็นเจ้าของนิยามคอลัมน์/Tool/Rule (กลุ่มเล็ก) เพื่อกันการเปลี่ยนที่กระทบสายการผลิต?
  8. โครงสร้างพื้นฐาน: เสิร์ฟจาก build (ไม่ใช้ dev server), HTTPS, Redis/Socket.IO แบบเดิมใช่หรือไม่?

15การพิมพ์สลีปในระบบใหม่

สลีปเป็น "Tool" ฝั่ง server (print.slip) ไม่ผูกกับเบราว์เซอร์ จึงพิมพ์ได้แม้ไม่มีใครเปิดหน้าเว็บ

เซลล์ถูกกรอก / RFID สแกน / ผู้ใช้กดปุ่ม 🖨️→ Tool print.slip ดึงข้อมูลจาก DB ตอนนั้น→ สร้างสลีป (หลายวัตถุดิบ + QR ต่อตัว)→ print-agent → เครื่องพิมพ์ของจุดนั้น→ บันทึก ToolRuns
  • 3 วิธีสั่งพิมพ์: (1) อัตโนมัติจากกติกา "เมื่อเซลล์ X มีค่า → พิมพ์" เช่น เมื่อออกห้องเย็น (2) ปุ่ม 🖨️ ในแถว/คอลัมน์ชนิด tool สำหรับพิมพ์ซ้ำ (3) จาก RFID Gateway ตอนสแกนรถเข็น
  • รถเข็น 1 คันหลายวัตถุดิบ = สลีปใบเดียว พิมพ์ทุกตัว มี QR ต่อวัตถุดิบ และย่อขนาดอัตโนมัติ — ใช้ตรรกะที่ทำไว้ใน print-agent เดิม (materials[])
  • QR บนสลีปคงรูปแบบเดิม (รหัสวัตถุดิบ | batch | batch_before | mapping_id | น้ำหนัก | kg | PFCM) เพื่อให้สแกนกลับเป็นข้อมูลนำเข้าของคอลัมน์ scan_or_type ได้ (เช่น หน้า Check In บรรจุ) สลีปเก่าที่พิมพ์ไปแล้วจึงยังใช้ได้
  • ข้อมูลสลีปมาจาก DB ณ ขณะสั่งพิมพ์ ไม่ใช่ข้อมูลที่ค้างในเบราว์เซอร์ (ระบบเดิมต้อง snapshot ฝั่งหน้าเว็บก่อนรถออกจากช่อง เพราะดึงสดแล้วหายไป) ระบบใหม่เก็บ slip_snapshot ลง ToolRuns เพื่อพิมพ์ซ้ำตรงกับต้นฉบับได้
  • เครื่องพิมพ์ต่อจุด: ตั้งในชีต Devices (printer_host / share / dot width เหมือน RFIDReaderConfig เดิม) เปลี่ยนจากหน้าเว็บ ไม่ต้องแก้โค้ด
  • รูปแบบสลีปปรับได้: เทมเพลตสลีปเก็บเป็นข้อมูล (เลือกคอลัมน์ที่จะแสดง, หัวข้อ, ขนาด) แทนการฮาร์ดโค้ดใน server.js ของ print-agent
  • กันพิมพ์ซ้ำ: ใช้ idempotency key (แถว + เหตุการณ์ + เวลา) พิมพ์ซ้ำโดยตั้งใจต้องกดปุ่มเองและถูกบันทึกว่าเป็น "พิมพ์ซ้ำ" โดยใคร
  • ถ้าเครื่องพิมพ์ใช้ไม่ได้: งานพิมพ์ค้างในคิว (ToolRuns.status = pending) ลองใหม่อัตโนมัติ และแสดงเตือนในตาราง ไม่หายเงียบ

16รวมฐานข้อมูลเดิม (PFCMv2) กับของ DocHUB ได้ไหม

ตอบสั้น: ได้ — และแนะนำทางที่ "รวมแบบมี schema แยก" ไม่ใช่แปลงตารางเดิมทั้งหมดเป็นแถว/เซลล์ของ DocHUB
ทางเลือกอธิบายข้อดีข้อเสีย
A. คนละ DB ใน SQL Server เดียวกันPFCMv2 และ DataSheetPro อยู่ใน instance เดียว ใช้ view/query ข้าม DB (PFCMv2.dbo.X) เร็วที่สุด เสี่ยงต่ำ ไม่แตะ PFCMv2; ทรานแซกชันข้าม DB ใน instance เดียวทำได้ข้อมูลอยู่สองที่; ต้องเช็ค collation ให้ตรงกัน
B. DB เดียว แยก schema (แนะนำเป้าหมายระยะยาว)ย้ายตาราง DocHUB ไปอยู่ schema sheet ใน PFCMv2 (หรือสร้าง DB ใหม่ที่มี pfcm + sheet) ชื่อไม่ชนกัน, JOIN ตรงๆ, backup/restore ครั้งเดียวต้องแก้โค้ด DocHUB ให้ระบุ schema; โหลดรวมที่ DB เดียว
C. แปลงตาราง PFCM เป็น Rows/Cells ทั้งหมดให้ TrolleyRMMapping, History ฯลฯ กลายเป็นข้อมูลในชีต รวมเป็นโมเดลเดียวไม่แนะนำ: ตารางธุรกรรมที่ RFID เขียนถี่จะช้า (EAV), ต้องเขียนตรรกะเดิมใหม่ทั้งหมด, ความเสี่ยงสูงสุด

แนวทางที่แนะนำ: ชีตเป็น "หน้าต่าง" ไปยังตารางจริง

  • ตารางธุรกรรมเดิม (TrolleyRMMapping, History, Slot, RFID_to_Trolley ฯลฯ) ยังเป็นเจ้าของข้อมูลเหมือนเดิม
  • ชีต Flow Board ชนิด "ชีตผูกตาราง" (bound sheet): คอลัมน์ผูกกับคอลัมน์จริงของตาราง/วิว การแก้เซลล์ผ่าน Tool ที่เรียกตรรกะเดิม ไม่เขียน EAV — ได้หน้าตาและสิทธิ์/ประวัติแบบ DocHUB โดยไม่ย้ายข้อมูลธุรกรรม
  • ข้อมูลหลักที่เปลี่ยนไม่บ่อย (วัตถุดิบ, แผนการผลิต, ห้องเย็น, ผู้ใช้) ค่อยย้ายเป็นชีตปกติหรือชีตผูกตารางก็ได้ตามความเหมาะสม
  • ชีตที่ผู้ใช้สร้างเอง (คอลัมน์เพิ่มเอง, ข้อมูลเสริม) ใช้ EAV ของ DocHUB ตามปกติและอ้างอิงตารางหลักผ่านคอลัมน์ relation (เช่น mapping_id)

สิ่งที่ต้องจัดการเมื่อรวม

ประเด็นรายละเอียด / วิธีจัดการ
ชื่อตารางชนกันทั้งสองระบบมีตาราง Users (PFCM: user_id + bcrypt, DocHUB: user_id แบบ GUID + RefreshTokens) และชื่อทั่วไปเช่น Folders, Notifications, Rows, Columns — ใช้ schema แยก (sheet.*) และตารางแมป UserMap(pfcm_user_id ↔ sheet_user_id)
การล็อกอินผู้ใช้ชุดเดียว: ให้ผู้ใช้ PFCM เดิมล็อกอินด้วยรหัสเดิม (ตรวจ hash เดิม แล้วออก JWT ของระบบใหม่) ต้องเช็คว่า hash ของ DocHUB เข้ากันกับ bcrypt เดิมหรือไม่ — ผมยังไม่ได้ตรวจในโค้ด
CollationDocHUB ใช้ Thai_CI_AS (ตามสคริปต์สร้าง DB) ต้องตรวจ collation ของ PFCMv2 ก่อน ถ้าต่างกัน JOIN ข้าม DB/ตารางจะ error ต้องแก้ด้วย COLLATE หรือปรับให้ตรงกัน
ประเภทคีย์PFCM ใช้ INT/VARCHAR (เช่น tro_id = '0868', mapping_id เป็น int) DocHUB ใช้ UNIQUEIDENTIFIER — เก็บรหัสเดิมเป็นคอลัมน์ธุรกิจ (entity_key) ไม่แทนที่ด้วย GUID
โหลดและ connection poolRFID เขียนถี่ + ตารางหลายผู้ใช้พร้อมกัน บน instance เดียว — แยก connection pool ต่อบริการ, ตั้งดัชนี, ตรวจ deadlock; ระบบเดิมตั้ง pool max 2000 ซึ่งสูงมาก ต้องทดสอบโหลดก่อนรวม
สิทธิ์ใน DBใช้ login/ผู้ใช้ DB แยกต่อบริการ สิทธิ์ขั้นต่ำ (ห้าม sa); ชีตผูกตารางได้สิทธิ์ตามตารางที่ระบุเท่านั้น
การเปลี่ยน schema บน productionตามกฎ CLAUDE.md: ต้องมีแผน rollback, ให้ DBA ทำ, ทดสอบบน DB สำเนาก่อน; เริ่มด้วยทางเลือก A (ไม่แตะ PFCMv2) แล้วค่อยพิจารณา B

ลำดับที่แนะนำ

  1. ขั้น 1: สร้าง DataSheetPro เป็น DB แยกใน instance เดิม ตรวจ collation และสร้างวิวอ่านอย่างเดียวของ PFCMv2 → ทำ Flow Board แบบอ่านอย่างเดียว
  2. ขั้น 2: เพิ่ม "ชีตผูกตาราง" + Tool ที่เรียกตรรกะเดิม (รวม print.slip) ทดลองกับงานเดียว รันคู่ขนาน
  3. ขั้น 3: เมื่อเสถียร พิจารณารวมเป็น DB เดียวแยก schema (ทางเลือก B) ผ่านแผนของ DBA
